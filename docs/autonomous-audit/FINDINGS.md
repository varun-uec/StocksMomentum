### Finding B1-001
- Capability: Technical Indicators
- Severity: LOW
- Type: Dead code / architecture drift risk
- Description: `backend/src/momentum25/domain/indicators/pipeline_impl.py` defines `IndicatorPipelinePlaceholder`, a class whose `compute()` always returns an `IndicatorSet` with every field `None`. It is exported from `domain/indicators/__init__.py` (`__all__ = ["IndicatorPipeline", "IndicatorPipelinePlaceholder"]`) but is not imported or instantiated anywhere else in the codebase (`grep -rn "IndicatorPipelinePlaceholder" backend/src` returns only the definition file and the `__init__.py` export). The real, fully implemented indicator pipeline is `IndicatorPipelineImpl` in `backend/src/momentum25/infrastructure/pipelines/indicator_pipeline.py` (RSI via `_rsi`/`_rsi_series`, MACD via `_macd`/`_macd_series`, ATR, ADX, Stochastic, Williams %R, CCI, ROC, ADR%, SMA/EMA, swing levels, etc. — real pandas/numpy math, not stubs). `IndicatorPipelineImpl` is wired through `interface/api/dependencies.py`, `dependencies_research.py`, `dependencies_validation.py`, `app/services/market_sync.py`, and `app/services/screening_job.py` — i.e. it is the production path for screening runs, live stock analysis, validation, research, and market sync.
- Expected behavior: Per Hexagonal Architecture (CLAUDE.md), the domain layer should hold only the `IndicatorPipeline` port (Protocol) — no infra-style "impl" class, real or placeholder, belongs in `domain/`. A placeholder left in the domain package after the real infrastructure implementation shipped is stale scaffolding.
- Observed behavior: The placeholder class still exists, is exported, and is architecturally positioned to look like "the" domain-side implementation, even though production code never calls it. `/securities/{symbol}/ohlcv` and the `/stocks/{symbol}/indicators/series` API (served via `stocks.py`, not `securities.py`) both resolve through `GetIndicatorSeries` → `IndicatorPipelineImpl`, so the frontend catalogue (`web/src/lib/indicators/catalogue.ts`) and dashboard/analysis pages receive real computed values, not `None`.
- Reproduction steps: `grep -rn "IndicatorPipelinePlaceholder" backend/src` — only 2 hits, both non-executing (definition + `__all__` export). `grep -rn "IndicatorPipelineImpl" backend/src/momentum25/interface/api/dependencies.py backend/src/momentum25/app/services/*.py` — 6+ live wiring hits.
- Evidence: `backend/src/momentum25/domain/indicators/pipeline_impl.py:16-43` (placeholder, always returns `IndicatorSet(as_of=as_of)` with no other fields set); `backend/src/momentum25/infrastructure/pipelines/indicator_pipeline.py:93-520` (real `_sma`, `_ema`, `_rsi`/`_rsi_series`, `_atr`/`_atr_series`, `_adx`, `_macd`/`_macd_series`, `_adr_pct`, `_stochastic`, `_williams_r`, `_cci`, `_roc`); `backend/src/momentum25/interface/api/dependencies.py:66,282,303,372,455,490` (production wiring of `IndicatorPipelineImpl`); `backend/src/momentum25/interface/api/routers/stocks.py:56-70` (`/stocks/{symbol}/indicators/series` route uses `GetIndicatorSeries` → real pipeline); test coverage — `grep -rln "IndicatorPipelineImpl" backend/tests` hits 11 integration/unit test files (e.g. `test_indicator_pipeline.py`, `test_live_stock_analysis.py`, `test_vertical_slice.py`); `grep -rln "IndicatorPipelinePlaceholder" backend/tests` returns zero files.
- Root cause: The placeholder was scaffolding for an early milestone (per its own docstring: "The full indicator math ... is implemented in milestone M2"). M2 shipped the real implementation in `infrastructure/pipelines/indicator_pipeline.py` instead of updating this file, and the placeholder was never deleted or reconciled with the port.
- Recommended action: Delete `backend/src/momentum25/domain/indicators/pipeline_impl.py` and its export in `domain/indicators/__init__.py`. Confirm `IndicatorPipeline` (the Protocol in `domain/indicators/pipeline.py`) is satisfied by `IndicatorPipelineImpl` and used as the sole port-conforming implementation. This is dead-code removal only — no production behavior changes, since nothing calls the placeholder today.

### Finding B3-001
- Capability: Walk-Forward Backtesting (CLI/API consistency)
- Severity: LOW
- Type: Interface inconsistency
- Description: The `POST /backtest/walk-forward` API route explicitly rejects `start > end` with a 422 (`interface/api/routers/backtest.py:53-57`), but the CLI `walk-forward` command (`interface/cli/main.py:59-83`) performs no such check before calling `runner.run(start_date, end_date, ...)`. Tracing `WalkForwardRunner.run` → `_first_session_of_each_month` (`application/use_cases/walk_forward.py:337-348`): with `start > end`, every session date fails `d < start or d > end` and the loop filters everything out, so `rebalance_dates` is `[]`. The run then silently completes with zero rebalances, zero trades, `final_nav == initial_capital`, `total_return == 0`, printed via `format_walk_forward_report` with no error or warning — a reversed date range looks identical to "no trading occurred," not a rejected input.
- Expected behavior: Per the API's own validation and general resilience practice for malformed requests, an invalid range (`start > end`) should be rejected with a clear error on both entry points that share the same wiring, per this module's own stated goal ("the two surfaces can never drift apart").
- Observed behavior: API rejects; CLI silently no-ops and reports a spurious 0% return as if a valid, empty backtest ran.
- Reproduction steps: `momentum25 walk-forward 2024-06-01 2024-01-01` (start after end) — completes normally, prints "Rebalances: 0, Trades: 0" and "Total return: 0.00%" instead of erroring.
- Evidence: `backend/src/momentum25/interface/cli/main.py:59-83` (no comparison of start/end before calling the runner) vs `backend/src/momentum25/interface/api/routers/backtest.py:53-57` (`if body.start > body.end: raise HTTPException(422, ...)`).
- Root cause: The `start > end` guard was added only at the new API DTO/router layer when the backtest API was built; the pre-existing CLI command was never given the equivalent guard.
- Recommended action: Add the same `start > end` check to `_run_walk_forward` in `main.py` (raise `typer.BadParameter` or echo an error and `typer.Exit(1)`), matching the API's behavior — a small, low-risk parity fix, not a methodology change.
- Autonomous fix allowed? YES (adds an input-validation guard identical in intent to the existing API check; no change to backtest math)
- Status: VERIFIED — see VERIFICATION_LOG.md

- Severity: OBSERVATION
- Type: Review summary
